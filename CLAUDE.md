# SideCar Monitor

## How we work: we decide things together

- **Propose before building.** For anything beyond a small, clearly requested change, describe the plan in a few lines and wait for agreement before writing code, installing things, or creating resources.
- **Check in at each milestone.** Don't chain several big steps (new projects, new packages, cloud resources, architecture changes) in one go. Finish one, show it, and ask before starting the next.
- **Surface decisions instead of making them silently.** When there's a real choice (technology, design, trade-offs, or limits discovered along the way), lay out the options with a recommendation and let the user pick.
- **Talk it through in chat.** Never use pop-up question dialogs or multiple-choice prompts. Ask in plain conversation and give your recommendation.
- **Ask before anything that costs money or touches shared or external systems:** Azure resources, role assignments, system installs.
- **Commit and push checkpoints** at good milestones, when things build and work. Suggest the checkpoint, then commit and push to `origin/main`. Never commit secrets: settings live in `%APPDATA%`.
- **Keep updates short and plain** so it's always clear what was done and what's next.

## Project

- WinUI 3 / .NET 10 kiosk app in `src/SideCarMonitor`, running full screen on a ~7" 1920×1080 **touchscreen** at 100% Windows scaling. Use big touch targets. All sizes come from `UiScale.cs` (`display.uiScale`, default 2.5). Nothing should be keyboard-only.
- Settings and credentials are in `%APPDATA%\SideCarMonitor\settings.json`, never in the repo.
- Home screen of Windows Phone-style tiles: Cameras (Reolink Home Hub, live RTSP via LibVLC plus motion/AI polling), Activity, Weather (Tempest local UDP 50222), Calendar (placeholder), Settings.
- Weather has two sources. Live readings come from the hub's local UDP broadcasts (`Services/TempestListener.cs`, no token). Forecast and history come from the WeatherFlow cloud (`Services/TempestCloud.cs`, only when `weather.tempestToken` is set; the station and Tempest device are found from the token, or `weather.tempestStationId`): `better_forecast` (~220 hourly + 10 daily, requested in metric) and the last 24 hours of one-minute `obs_st` readings summarized per hour, plus the station's own rain today/yesterday. It refreshes every 30 minutes (5 after a failure), is cached in `%LOCALAPPDATA%\SideCarMonitor\weather-outlook.json`, and failures are System events (once per 6 hours). The token goes in the query string, so never log request URLs. The agent's `get_weather_forecast(hours, days, pastHours)` and the briefs' `weather_coming` facts (highlights: low/high, freeze, big swing, strongest gusts, best precip chance) come from it.
- Weather alerts: `Services/WeatherAlerts.cs`, thresholds in `weather.alerts` (°F, mph and miles whatever the display units; 0 turns a rule off). Live rules run on each Tempest reading: gusts ≥ `gustMph` (20), a drop of `tempDropF` (8) within `tempDropMinutes` (30), `colderThanForecastF` (10) below the interpolated hourly forecast, rain/hail starting after `dryMinutesBeforeStart` (60) dry (the sensor can't detect snow, so near freezing it says "Rain or snow", or "Snow or sleet" if snow is forecast), and lightning within `lightningMiles` (10). Forecast rules run on each forecast update and every 5 minutes: rain/snow at ≥ `precipChancePercent` (50) within `precipComingHours` (2), and gusts ≥ `gustMph` within `windComingHours` (6). Each kind has a `cooldownHours` (3) cooldown, but a markedly worse reading (gusts 10 mph stronger, lightning 3 miles closer) alerts again; forecast alerts fire once per forecast event. Cooldowns are saved in `%LOCALAPPDATA%\SideCarMonitor\weather-alerts.json`. Every alert goes to Activity (`Source` "weather", Weather filter, worth a look). The kiosk popup (with a Weather button) shows unless someone is using the kiosk, and the alert is spoken (or chimes) except during quiet hours `quietFrom`–`quietUntil` (22–7). Briefs get the day's alerts in `activity.weatherAlerts`. Phone: `reminders/WeatherAlerts.kt` reads `/api/status` every 15 minutes and on open and posts one notification per new weather alert from the last 3 hours (channel "Weather alerts", clears itself after 3 hours; the watch mirrors it). Status items carry `detail`, and the phone's Activity has a Weather filter.
- Weather page tabs: Now (the live tiles, `WeatherNowGrid`), Hourly and 10 days (`Controls/WeatherForecastView`, built in code). Hourly is a sideways strip: the past 12 hours plus the current hour so far from the station ("Actual", "Now · so far"), then 48 forecast hours. Tap a card for details; the strip opens scrolled to Now. 10 days lists high/low, conditions, precip and sunrise/sunset; tapping a day jumps Hourly to it. Emoji icons come from WeatherFlow's icon names. The Weather tile shows a look-ahead line (`WeatherTileNext`: rain/snow likely or strong gusts in the next 12 hours, else today's high or tonight's low). Both redraw on each forecast download and when the hour turns.
- Build: `dotnet build src/SideCarMonitor/SideCarMonitor.csproj`. The .NET SDK is in `C:\Program Files\dotnet` (may not be on PATH in older shells).
- `src/SideCarAgent`: a Copilot SDK agent that sends model calls to the Foundry `model-router` deployment (BYOK, Entra token supplied by the kiosk). It talks to the kiosk with JSON lines over stdin/stdout. Tools whose data lives in the kiosk (e.g. `get_local_weather`) are answered by the kiosk over that pipe.
- The kiosk (`Services/AgentHost.cs`) runs the agent in an **MXC ProcessContainer sandbox** (`assistant.sandbox`, default true; never fall back to unsandboxed silently):
  - files: read-only program folder and .NET runtime; read/write only `%LOCALAPPDATA%\SideCarAgent`
  - network: direct egress denied; the only route out is `AllowlistProxy` (127.0.0.1), which allows just the Foundry host
  - UI: clipboard and input injection blocked (basic window-system init must stay allowed or the runtime crashes with 0xC0000142)
  - `MxcProcess.WaitAsync` drains the output streams, so only call it after stdout ends
  - policy changes go through Learning Mode evidence and the user's approval
- To-do list: rules live in `src/SideCarTasks` and are unit tested in `tests/SideCarTasks.Tests` (`dotnet test`). That covers date math in the saved timezone, the midnight roll (every open to-do from an earlier day moves to today after today's own, audited and undoable; a missed hard deadline rolls too, flagged `MissedDeadline`; after `RollDaysBeforeAsk` = 7 days of rolling it also lands in Needs me; there's no Today pin any more, old pins become dated today), actor-based authorization (only the user marks tasks done), versioned deliverables and idempotent daily jobs, and a per-day order you set by dragging (`DayRank`, `OrderDay`, `TaskService.InDayOrder`: dragged order first, then priority; `POST /api/tasks/order`). On the phone's weekly plan, days collapse while you drag and the day you hold over opens so you can drop at an exact spot. The kiosk's `TaskAssistant` answers the agent's task tools: turns starting with `review-` are background reviews, can only act on that one task, and only add notes, deliverables or questions. The kiosk checks the daily jobs every minute; they also run headlessly via the Windows scheduled task "SideCarMonitor daily jobs" (`SideCarMonitor.exe --jobs`, 12:05 AM and every 6 hours). The weekly plan is the main to-do view on the kiosk and phone (Needs me / Done one tap away). Data: `%APPDATA%\SideCarMonitor\tasks.json`.
- Watch app: `android/wear` (Compose for Wear OS 1.6.x, because 1.7 needs AGP 9.1+). It has the same applicationId as the phone app, so the Wear data layer connects them. The watch never talks to the kiosk itself: it uses the phone's `wear/WatchBridgeService` (MessageClient RPC for home/done/ask; ChannelClient streams for voice, WAV up, `[len][json][WAV]` back). It has a tile (`SideCarTileService`) and a temperature complication. To test without hardware, use the emulator AVD `SideCarWatch` (Wear OS 6, x86_64).
- Agent replies can contain several `message` events around tool calls; a turn is only finished at `idle`.
- Phone outbox (`data/Outbox.kt`): nothing sent from the phone is lost. Every write is saved first and sent with an `Idempotency-Key`; if the kiosk is out of reach it waits and is retried on network back, app open, and by WorkManager (network required, backoff). The kiosk (`Services/IdempotencyCache.cs` middleware, 72 h, `idempotency.json`) replays the first answer for a repeated key. 4xx refusals aren't retried (shown with the reason). Chat messages and voice recordings queue too and are answered by `POST /api/ask` (reply into the chat, or a notification); a chat message over an hour old asks Send / Discard. Covers task actions, notes and dictation, reminders (incl. notification buttons), feed actions and tags, ideas, calendar, house, and the watch's Done and questions.
- Phone app: `android/app` (Kotlin + Compose). Phone assistant is a chat (`ui/ChatScreen.kt`, opened by the chat button or the SideCar tile): bubbles, light markdown with tappable links, tool-activity chips, suggestions, New chat, Stop; the mic button switches to voice mode (spoken replies and hands-free follow-ups; typed chats aren't spoken). Phone voice records until 2.5 s of silence (90 s max) and, when started by voice, reopens the mic after each reply like the kiosk; Speak buttons dictate task notes and answers. Meeting heads-ups (`reminders/MeetingAlerts.kt`): prep notification ~30 min before and Join at 5 min, scheduled from `/api/meetings` on each reminder check; the clock tile shows the next meeting and turns amber. Briefings remember their position (`data/PlaybackMemory.kt`). Parity screens: X (`/api/x/*`, briefing with Tag, Actions per post), Day view from the clock tile (`/api/calendar/day`, `/api/calendar/add`), the latest brief card with Play (`/api/brief*`), Activity filters. Pairs with the kiosk gateway (`Services/Gateway.cs`, HTTPS :8443, pinned self-signed cert + bearer key from the QR code). Build with `gradlew.bat assembleDebug` using Android Studio's JBR as `JAVA_HOME`; the SDK is in `%LOCALAPPDATA%\Android\Sdk`. `cmd` can't run `gradlew.bat` here, so launch it via `Start-Process`, and pass `--no-daemon`: `Start-Process -Wait` otherwise waits on the Gradle daemon forever.
- Camera event pictures: `Services/EventStore.cs` (`%LOCALAPPDATA%\SideCarMonitor\events`, 7 days). Each picture is labeled by **Microsoft-Decision-1.1** (`Services/EventJudge.cs`, Foundry deployment `decision-dz`, DataZoneStandard; the GlobalStandard `decision` deployment is stuck at a 1K-token limit). Send images in the `assets` form (`image_url` data URIs are read as text, costing ~35K tokens), at least 280 px on each side, with a Content-Length header. The rate limiter estimates from request size, so keep pictures ~1024×288 and send one at a time.
- Home Assistant: the agent gets `home_tools`/`home_state`/`home_call`, answered by the kiosk's `Services/HomeAssistantBridge.cs` (HA's MCP server at `/api/mcp`, plain JSON-RPC). The token stays in the kiosk (`%APPDATA%\SideCarMonitor\ha-token.txt`, never committed, never printed). Every call goes to `home-actions.log`. Control actions are refused for background (review) turns, scored by the decision model for odd activity (a score of 0.6 or more blocks the action and pauses home control), and paused after a burst (8 actions in 2 minutes). Only the user can resume (kiosk banner).
- Activity is one feed (`MotionEvent` with `Source`): camera events, house events from Home Assistant's WebSocket event stream (`Services/HomeEventStream.cs`: locks, doors and windows, garage and gates, alarms, leaks and smoke, automations; no lights, media, sensor readings, motion or presence), and SideCar's own home actions. Door, lock and garage events are scored by the decision model (`OddHouseEventAsync`). The Activity tile opens its own page (`Controls/ActivityPage`: the feed plus a detail pane). Filters: All, Cameras, Doors, House, System. System events (`Services/SystemEvents.Report`) cover safeguards that stopped the agent (blocked home actions, refused review actions, denied network requests), pause and resume, agent sandbox start and crash, and cameras or Home Assistant going offline or recovering.
- LinkedIn tile: `Services/LinkedInReader.cs` (Playwright driving the installed Edge in a dedicated profile `%LOCALAPPDATA%\SideCarMonitor\linkedin-edge`, signed in with `--linkedin-login`; read-only; the window is placed off-screen because a minimized one doesn't load the feed; the feed scrolls its `<main>` panel; markup is `data-view-name=feed-full-update`). `Services/LinkedInFeed.cs` sorts posts with Microsoft-Decision (your last 24 Noise/Not noise labels are sent as examples), keeps people profiles, and has the agent write the digest and profile summaries as background `li-` turns (read-only for tasks, no home control). A Signal to noise line shows the last 14 days (signal %, ads %). The Sources tab lists people with 2+ posts that are mostly noise (30 days); Suppress keeps them out of Signal and briefings and skips the decision model for them (`suppressedAuthors`; their posts stay under Noise). It runs daily around 7:00 plus Run now, and stops on any sign-in or verification page. Data: `%APPDATA%\SideCarMonitor\linkedin.json`.
- Calendars: the CTC and PMCollab M365 calendars, through Microsoft Graph via the Entra app 'SideCar Calendar' (appId 41eef356-6325-4650-96e5-d925e07ff905, registered in the CTC tenant, multi-tenant public client, delegated Calendars.ReadWrite). Sign in with `SideCarMonitor.exe --calendar-login <Label>`; tokens are in the DPAPI MSAL cache in `%LOCALAPPDATA%\SideCarMonitor`; labels are in `%APPDATA%\SideCarMonitor\calendars.json`. Agent tools: `calendar_events`, `calendar_free_time` and `calendar_add`, answered by `Services/CalendarTools.cs`. `calendar_add` requires a user turn, allows at most one appointment per hour, runs the odd-activity check, and is logged to `calendar-actions.log` and System events. The kiosk clock tile shows the next meeting and turns amber 15 minutes before; a popup with Join appears 5 minutes before. Meeting heads-up: `Services/MeetingPrep.cs` has the agent write a prep note (background read-only `prep-` turn: who, context, related to-dos, conflicts, a web search on outside people when `assistant.meetingPrepWebSearch`, a goal) `assistant.meetingPrepMinutes` (30) before each real meeting (not all-day, free, declined or your own holds); shown and spoken on the kiosk, stored in `%APPDATA%\SideCarMonitor\meeting-prep.json`, served to the phone by `/api/meetings`. Attendee lists leave out your own addresses.
- Briefs: `Services/BriefService.cs` makes a morning brief (8 AM) and an evening brief (8 PM). The kiosk gathers the facts on the UI thread (weather, both calendars, to-dos, activity, house, LinkedIn digest); the agent writes the brief as a background `brief-` turn (read-only). The brief shows full screen until dismissed; reopen it with Brief in the Day view. Stored in `%APPDATA%\SideCarMonitor\briefs.json`. When restarting the kiosk, stop SideCarMonitor before SideCarAgent, or a fake 'agent stopped unexpectedly' event is logged.
- Reminders: `Services/ReminderService.cs` (`%APPDATA%\SideCarMonitor\reminders.json`) with agent tools `reminder_add` (one-time or repeating: daily, weekdays, weekly:tue,thu or monthly), `reminder_list` and `reminder_done`; only user turns can add or close them. A due reminder shows a kiosk banner over every page until Done, Snooze (10 min, 1 hour, tomorrow) or To-do (pinned to Today); it's spoken when due and again every 15 minutes. Done on a repeating reminder schedules the next one. Phone: WorkManager checks `/api/reminders` every 15 minutes and on app open, and posts notifications with Done / 1 hour / To-do that re-alert until handled.
- X tile: official X API v2, pay-per-use (about $0.005 per post read). `Services/XClient.cs` uses OAuth 2.0 PKCE with the confidential app in `%APPDATA%\SideCarMonitor\x-client-id.txt` (line 1 id, line 2 secret); the token is DPAPI-encrypted in `%LOCALAPPDATA%\SideCarMonitor\x-token.bin`; sign in with `--x-login`. `Services/XFeed.cs`: there's no schedule; Update pulls up to 100 new posts since the last `since_id`. Decision-model Signal/Noise uses the interests in settings (`assistant.interests`) plus your labels. Per post: Save (bookmark), Replies analysis (up to 50 replies, background `xr-` turn), and Unfollow with confirm. The list builder tallies accounts. A Signal to noise line shows the last 14 days and how much of the noise comes from accounts that never post signal. The briefing has Tag (LinkedIn too, via `Services/BriefingTag.cs`): it saves an 'X Followup: <post headline>' to-do whose `Link` is the post (shown as Open item on kiosk and phone); what you say right after Tag is added as a note. The assistant tidies the title in the background unless the to-do changed. `/api/*/podcast/tag` (old `/interrupt` paths still accepted).
- Idea radar: `Services/IdeaRadar.cs` reads newly pulled LinkedIn and X posts every 10 minutes (background read-only `idea-` turns, 40 posts per batch) and keeps a ranked list in `%APPDATA%\SideCarMonitor\ideas.json`: PMCollab problems to solve, PMCollab features, and wild ideas, each with evidence (author, quote, post); repeats are merged as more evidence. PMCollab's description is `%APPDATA%\SideCarMonitor\pmcollab-profile.md` (no file, no radar). Ideas tile on the kiosk and phone home screens (one combined list, best first) and an Ideas tab on the LinkedIn and X pages (`/api/ideas`) with Make to-do ('PMCollab idea - ...' / 'Idea - ...') and Not useful (used as taste examples).
- PMCollab MCP: `Services/PmCollabMcp.cs` talks to https://dev1.pmcollab.ai/mcp/pmc as you (OAuth: dynamic client registration in `%APPDATA%\SideCarMonitor\pmcollab-client.json`, PKCE sign-in with `--pmcollab-login` on 127.0.0.1:53683, token DPAPI-encrypted in `%LOCALAPPDATA%\SideCarMonitor\pmcollab-token.bin`; `--pmcollab-tools <out.json>` lists the tools). SideCar is an agent principal there (grant with pmc:brain:write). Send to PMCollab on an idea (kiosk and phone, `/api/ideas/{id}/action` `pmcollab`) calls `brain_signal_submit` once: title line, pitch, analysis, evidence with links, marked as agent-found; the signal id is kept on the idea and it's never resent (the tool isn't retry-safe; a timed-out send shows 'check your Brain'). `--pmcollab-call <tool> <args.json> <out.json>` makes one call for checking. Server: `assistant.pmcollabMcp`.
- Flights: agent tool `flight_search` → `Services/FlightSearch.cs` (Duffel API; token in `%APPDATA%\SideCarMonitor\duffel-token.txt`; `duffel_test_` only returns Duffel's sample airline ZZ). It's read-only: offer requests per date or date pair (up to 9), ranked by stops, then price, then duration, plus seat maps for the top few. The exit-row rule: a seat row right behind an `exit_row` element is an exit row; it reclines unless another exit row follows it (e.g. United 737 row 21 reclines, row 20 doesn't). Travel to-dos: on Take a pass, the agent saves the top 3 options as the deliverable; it never books.
- Web search: agent tool `web_search` → `Services/WebSearch.cs`. The kiosk calls the Foundry project Responses API (`https://{account}.services.ai.azure.com/api/projects/{assistant.foundryProject}/openai/v1/responses`) with the built-in `web_search` tool (Web IQ / Bing), using the model-router deployment and the kiosk's Entra token (scope `https://ai.azure.com/.default`). It returns an answer plus sources; searches are logged as System events. To-do passes and the briefings can use it.
- Voice assistant: floating mic button → MAI-Transcribe-2-Streaming (listen) → agent → MAI-Voice-2.1-Flash (speak), Azure Speech on the same Foundry resource. Listening keeps going through pauses and ends after `assistant.endSilenceSeconds` (2.5) of silence or Done. A conversation started by voice reopens the mic after each spoken reply until `assistant.followUpSeconds` (8) of silence, an end phrase ("that's all", "thanks", "stop"), Stop or close.
- Briefing playback (LinkedIn, X, morning/evening brief) remembers its position (`Services/PlaybackMemory.cs`, `%LOCALAPPDATA%\SideCarMonitor\playback.json`) and resumes after a restart; a half-played episode is finished before a new one is made.
